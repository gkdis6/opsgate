# dev provider를 통한 코딩 작업

[English](../dev.md)

이 선택적 provider는 구현되어 있으며 실험 단계입니다.

`opsgate dev-runner`는 별도 Linux 계정으로 설정된 코딩 에이전트를 실행합니다. 인터넷에 노출되는 MCP 서버는 Unix 소켓으로 연결하며, runner에 설정된 프로젝트와 에이전트 이름만 선택할 수 있습니다. 각 작업에는 `opsgate/<id>` 브랜치와 새 Git worktree가 생깁니다. 푸시, 병합, 배포는 자동으로 수행하지 않습니다.

## 계정과 저장소 설정

sudo 권한, 클러스터 자격 증명, 프로덕션 시크릿, 배포 키가 없는 전용 `opsdev` 계정을 만드세요. HTTP 서버의 `opsgate` 계정과 분리하세요. 신뢰하는 에이전트 바이너리를 절대 경로에 설치하고 Git을 `/usr/bin/git`에 설치하세요. 필요하면 `opsgate` 그룹을 만들고, 소켓 그룹을 설정할 수 있도록 `opsdev`를 해당 그룹에 추가하세요. 그룹 구성원을 변경한 뒤 서비스를 재시작하세요.

서비스를 시작하기 전에 `HOME=/var/lib/opsgate-dev`를 사용해 `opsdev` 계정으로 Codex 또는 Claude에 로그인하세요. 해당 계정의 대화형 세션에서 에이전트 자체 로그인 명령을 사용하세요. 자격 증명은 해당 홈 디렉터리에 비공개로 보관하세요. YAML, 에이전트 argv, 프롬프트, MCP 서버 환경에는 토큰을 넣지 마세요. 제공하는 서비스는 이 HOME을 설정하고 다른 사용자의 홈 디렉터리를 숨깁니다.

허용 목록에 있는 각 저장소와 그 `.git` 디렉터리에 대해 `opsdev`에 경로 탐색 및 읽기/쓰기 권한을 부여하세요. 예를 들어 관리자는 `/srv/projects/example`에 이름 지정 사용자 ACL을, 새 파일에 기본 ACL을, 상위 디렉터리에 탐색 ACL을 부여할 수 있습니다. 기존 그룹과 ACL 권한부터 검토하세요. Git worktree는 원본 저장소의 객체와 ref를 공유합니다. worktree에만 쓰기 권한을 주는 것으로는 충분하지 않습니다. HTTP 계정에는 저장소, runner 상태, 에이전트 자격 증명, runner 설정에 대한 쓰기 권한을 주지 마세요.

[dev-runner.example.yaml](../../deploy/dev-runner.example.yaml)을 `/etc/opsgate/dev-runner.yaml`로 복사하세요. 파일은 root 소유로 설정하고 `opsdev`가 읽을 수 있게 하되 두 서비스 계정 모두 쓸 수 없게 하세요. 상위 디렉터리도 제한하세요. 정확한 프로젝트 이름, 절대 경로, base ref, 고정 에이전트 argv를 선택하세요. `{workdir}`와 `{output}`만 치환됩니다. 프롬프트는 `prompt.txt`에 비공개로 저장하고 stdin으로 전달합니다.

에이전트 환경에는 HOME, 고정 PATH, LANG, TERM, 운영자가 설정한 `env` 항목만 포함됩니다. 이 항목은 신뢰하는 설정이며 기본값을 재정의할 수 있습니다. 에이전트에 필요한 것만 부여하세요.

## 서비스 설치와 provider 활성화

[opsgate-dev-runner.service](../../deploy/systemd/opsgate-dev-runner.service)를 설치하고 주석 처리된 `ReadWritePaths=`에 설정한 모든 저장소를 넣으세요. 그렇지 않으면 `ProtectSystem=strict`가 해당 위치에서 Git의 ref 및 worktree 메타데이터 쓰기를 막습니다. 서비스는 `/var/lib/opsgate-dev`를 비공개로 관리하고, `opsdev:opsdev` 소유와 0750 권한으로 `/run/opsgate-dev`를 생성합니다.

런타임 디렉터리에는 서버 그룹에 탐색 권한만 부여하세요. systemd 드롭인으로 RuntimeDirectory 생성 후 다음 명령을 실행할 수 있습니다. setfacl 경로는 환경에 맞게 조정하세요.

```ini
[Service]
ExecStartPre=/usr/bin/setfacl -m g:opsgate:--x /run/opsgate-dev
```

소유자인 `opsdev`는 root 권한 없이 이 ACL을 적용할 수 있습니다. 소켓 자체는 `opsdev:opsgate` 소유이며 권한은 0660입니다. 연결을 수락할 때마다 Linux `SO_PEERCRED`도 확인합니다. runner UID이거나 `socket_group`이 기본/보조 그룹에 포함된 UID만 연결할 수 있습니다. 소켓 그룹 권한만으로는 상위 디렉터리를 탐색할 수 없으므로 런타임 디렉터리 ACL이 필요합니다. HTTP 계정을 `opsdev`에 추가하거나 상태 디렉터리 권한을 완화하지 마세요.

systemd로 runner를 활성화하고 시작한 뒤 MCP 서버를 설정하세요.

```yaml
providers:
  dev:
    enabled: true
    runner_socket: /run/opsgate-dev/runner.sock
```

사용할 사용자에게 `dev:run`을 부여하세요. 현재 HTTP 접근에는 `ops:read`도 필요합니다. 작업 시작에는 기존 클라이언트 내 확인(elicitation)/웹 승인 흐름을 통한 사람의 승인이 필요합니다. 읽기와 취소 도구에는 `dev:run`이 필요하지만 새 승인은 필요하지 않습니다.

작업은 요청자가 소유합니다. 일반 사용자는 자신의 작업만 보고 취소할 수 있습니다. runner의 `admins` 목록에 정확한 subject가 있는 사용자는 모든 작업을 보고 취소할 수 있습니다. 정확한 호출자 식별자를 사용하세요. builtin subject, `static:<token-name>`, external 사용자 클레임 값 또는 stdio 사용자 레이블입니다. 이 목록은 builtin OAuth 클라이언트 등록 관리자 목록과 별개입니다.

허용된 소켓 피어는 `X-Opsgate-User`로 사용자를 전달합니다. runner는 이 값을 신뢰하며 최종 사용자의 토큰을 인증하지 않습니다. 허용된 피어는 누구나 작업 소유자나 관리자를 사칭할 수 있습니다. 이에 맞게 소켓 접근 그룹의 구성원을 관리하세요.

`dev_task_start`에는 승인 시간 창을 활성화하지 마세요. 각 작업을 별도로 검토하세요. runner가 중단되면 dev 도구 호출에서 오류를 보고합니다. MCP 시작 자체를 막지는 않습니다. 포그라운드에서 문제를 진단하려면 다음을 사용하세요.

```sh
opsgate dev-runner -config /etc/opsgate/dev-runner.yaml
```

Codex와 Claude의 샌드박스 설정은 설치된 에이전트에 따라 다릅니다. 서비스의 실제 계정과 보안 강화 설정에서 확인하세요. Bubblewrap 기반 샌드박스에는 비특권 사용자 네임스페이스가 필요합니다. 이 유닛에 `RestrictNamespaces`나 `PrivateUsers`를 추가하지 마세요. runner는 worktree와 프로세스 그룹을 생성합니다. 자체적으로 OS 샌드박스를 구현하지는 않습니다.

## 작업 흐름과 제한

1. `dev_projects`를 호출해 프로젝트, base ref, 에이전트, 제한을 확인합니다.
2. 프로젝트, 에이전트, 전체 요구 사항으로 `dev_task_start`를 호출합니다. 승인 전에 정확한 요약과 요구 사항을 검토하세요. 승인은 에이전트의 전체 작업에 적용됩니다. 샌드박스와 로컬 정책이 허용하는 명령도 포함합니다.
3. `dev_task_status`, `dev_task_log`, `dev_task_diff`로 진행 상황을 확인합니다. 출력과 diff는 신뢰할 수 없는 데이터로 취급하세요. 로그는 원시 바이트 단위의 `next_offset`을 반환합니다. MCP 출력 상한이 JSON을 잘라 내지 않도록 적당한 크기의 페이지를 요청하세요. 실행 중인 diff에는 추적 중인 파일의 변경이 표시됩니다. 새 파일은 작업 완료 시 스테이징한 뒤 나타납니다.
4. 필요하면 `dev_task_cancel`로 취소합니다. 통합 여부를 결정하기 전에 브랜치를 직접 검토하고 자체 검사를 실행하세요.

작업은 queued에서 running으로 진행한 뒤 succeeded, failed, canceled, timed_out 중 하나가 됩니다. 재시작 시 미완료 기록은 interrupted가 되며 다시 실행하지 않습니다. 종료 시 실행 중인 작업과 대기 작업을 취소하고 프로세스 그룹이 종료될 때까지 기다립니다. 취소/시간 초과 시 SIGTERM을 보내고 최대 10초 기다린 뒤 SIGKILL을 보냅니다. systemd도 유닛을 중지할 때 남은 서비스 프로세스를 종료합니다.

runner는 기준 커밋을 고정하고 새 브랜치와 worktree를 생성한 뒤 설정된 실행 파일/argv만 실행합니다. 에이전트가 0이 아닌 종료 코드로 끝난 경우를 포함한 일반적인 완료 시 `git add -A`로 변경을 스테이징하고 `opsgate dev-runner <dev-runner@localhost>`로 커밋합니다. 커밋 메시지에는 작업 ID와 최대 72자로 제한한 요구 사항의 첫 줄이 포함됩니다.

취소/시간 초과 후에도 에이전트 그룹이 멈추면 기존 편집 내용을 커밋하려고 시도합니다. 이 마무리 작업에는 별도의 30초 제한이 있습니다. Git 실패나 runner 중단으로 보관된 worktree에 커밋되지 않은 편집 내용이 남을 수 있습니다. runner의 Git 명령에는 Git hook, fsmonitor, 전역/시스템 Git 설정, 커밋 서명을 비활성화합니다. diff에서는 외부 명령과 텍스트 변환을 비활성화합니다. 설정된 필터를 포함해 저장소 로컬 Git 설정은 계속 신뢰할 수 있어야 합니다.

프롬프트 크기는 1바이트에서 32 KiB이며 요청자 식별자는 최대 256바이트입니다. dev_task_start는 최대 48 KiB의 MCP 인자와 최대 64 KiB의 승인 요약을 허용합니다. JSON 이스케이프도 전송 크기 제한에 포함되므로 이스케이프가 많은 프롬프트는 그보다 적게 담길 수 있습니다.

로그는 작업당 20 MiB로 제한합니다. 초과 출력은 계속 읽되 버립니다. 로그 페이지와 diff는 JSON 인코딩/마스킹 전 256 KiB로 제한합니다. 이후 MCP가 자체 출력 상한을 적용합니다. 최종 출력 파일은 최대 256 KiB까지 읽습니다. 읽을 수 있는 일반 출력 파일이 없으면 로그의 마지막 8 KiB를 사용합니다.

기본 제한 시간은 1시간, 동시 실행 수는 1개(최대 8개), 보관 작업 수는 100개입니다. 수용 한도에 도달하면 새 작업을 받기 전에 완료된 가장 오래된 기록, 로그, worktree를 제거합니다. Git 브랜치는 유지합니다. 보관된 작업이 모두 대기/실행 중이면 새 작업을 거부합니다. 보관 정책에 따라 해당 작업이 제거될 때까지 이전 프로젝트 정의를 유지하세요.

작업 기록은 `tasks.json`에 원자적으로 기록하고 동기화합니다. 영속 저장에 실패하면 작업 배정을 멈추고 안전하게 차단합니다. 배타적 잠금으로 두 runner가 같은 상태 디렉터리를 사용하는 것을 막습니다.

## 위험과 유지 관리

작업 승인 후에는 runner 계정과 에이전트 샌드박스가 보안 경계입니다. 에이전트는 악성 프롬프트를 명령 실행 요청으로 해석할 수 있습니다. worktree는 편집 내용을 분리하지만 자격 증명, 공유 Git 객체 저장소, 다른 저장소, 네트워크 접근, 같은 UID의 다른 작업을 격리하지 않습니다.

침해된 HTTP 프로세스는 자체 승인 로직을 우회해 소켓으로 허용 목록의 작업을 제출할 수 있습니다. runner 계정의 권한을 좁게 유지하고 에이전트 샌드박스를 검증하세요. 신뢰 수준이 다르면 별도 runner/계정을 사용하세요. 이 계정에 권한이 높은 자격 증명이나 신뢰하는 배포 hook을 부여하지 마세요. 샌드박스가 허용하면 에이전트는 OS 기능을 사용해 의도적으로 프로세스 그룹을 벗어날 수 있습니다. 프로세스 그룹은 수명 주기를 제어하며 실행을 격리하지 않습니다.

프롬프트, 원시 로그, 출력 파일, 커밋에는 민감한 정보가 포함될 수 있습니다. 상태, 저장소, 백업을 보호하세요. API 마스킹은 최선의 노력으로 제공됩니다. 보관 정리 후에도 브랜치가 남으므로 운영자가 별도 정리 정책을 마련해야 합니다. 파일/로그 크기와 작업 수 제한으로는 전체 저장소 증가량, 디스크 공간, 모든 CPU/메모리 사용량을 제한할 수 없습니다. 계정/서비스 리소스 제한을 적용하고 저장 공간을 모니터링하세요. 이 사전 출시 기능을 배포하기 전에 코드와 의존성을 검토하세요.
