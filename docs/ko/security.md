# 보안 정책

[English](../../SECURITY.md)

opsgate는 원격 HTTP, 인증, 사람이 승인한 쓰기를 구현했으며 첫 공개 릴리스를 준비하고 있습니다. 선택적 Obsidian 및 dev provider는 실험적입니다. 아직 제3자의 보안 검토를 받지 않았습니다. 배포하는 구현을 검토합니다.

## 위협 모델

**opsgate 인스턴스 하나는 신뢰 그룹 하나입니다.** `ops:read`는 활성화된 모든 읽기 provider의 서버, 클러스터 리소스, 노트를 읽습니다. provider 허용 목록은 리소스를 제한합니다. `server.tools`와 사용자별/토큰별 `tools` glob은 도구 접근을 좁힐 수 있습니다. 이들은 별도의 자격 증명 경계나 프로세스 경계가 아닙니다. 신뢰 수준이 다르면 인스턴스와 계정을 분리합니다. 예를 들어 프로덕션 운영, 개인 노트, 코딩 에이전트를 분리합니다. 각 인스턴스의 자격 증명과 접근 가능한 데이터는 신뢰 그룹 전체에 적절해야 합니다.

의도한 경계는 읽기 도구와 명시적으로 승인한 쓰기 작업을 갖춘 제한된 MCP 인터페이스입니다. provider의 명시적 활성화, unit 및 네임스페이스 허용 목록, 네임스페이스 거부 목록, 스코프 검사, 호출 및 출력 제한, 최선의 노력에 따른 마스킹, 호출별 감사 기록을 적용합니다. 임의의 셸이나 exec 인터페이스는 노출하지 않습니다. Kubernetes Secrets는 제외하며 ConfigMap 값은 기본적으로 숨깁니다. 이러한 통제는 우발적인 정보 노출과 클라이언트가 opsgate를 통해 요청할 수 있는 작업을 줄입니다.

이 통제가 신뢰할 수 없는 출력을 안전하게 만들지는 않습니다. 로그, 이벤트, 애너테이션, 리소스 이름에는 프롬프트 인젝션이 포함될 수 있습니다. 출력은 지시가 아닌 데이터로 취급합니다. 악의적이거나 침해된 클라이언트는 설정된 스코프와 허용 목록이 허용하는 모든 작업을 요청하고, 반환 데이터를 복사하거나 연결된 다른 도구를 공격할 수 있습니다. MCP 애너테이션은 힌트이며 인가가 아닙니다. stdio는 서버를 실행하는 OS 계정을 신뢰합니다. 설정된 사용자 이름은 레이블일 뿐입니다.

지나치게 넓은 RBAC이나 kubeconfig 권한은 버그와 침해의 영향을 키웁니다. 필요한 읽기 및 선택적 쓰기 권한만 있는 전용 자격 증명을 사용하고, 제공된 RBAC 매니페스트를 검토합니다. kubeconfig의 `exec` 및 `auth-provider` 자격 증명 플러그인은 거부됩니다. kubeconfig 파일과 설정 경로는 신뢰할 수 있는 소유자가 관리해야 합니다. 네임스페이스 허용/거부 규칙은 네임스페이스 범위 리소스와 Namespace 객체를 이름으로 필터링합니다. Nodes나 PersistentVolumes는 제한하지 않으며, `k8s_overview`의 노드도 마찬가지입니다. 클러스터 범위 종류에는 `namespace`를 생략합니다. 제공된 ClusterRoleBinding은 클러스터 전체 읽기를 허용합니다. 가능하면 네임스페이스 RoleBinding을 사용합니다. provider와 그 자격 증명을 공격자가 제어할 수 없어야 합니다. root 실행은 권장하지 않습니다. 필요한 journal 및 클러스터 접근만 가진 일반 계정을 사용합니다.

[도구 참조](tools.md#redaction-and-object-sanitization)는 구현된 텍스트 패턴과 객체 정리를 설명합니다. ConfigMap의 data 및 binaryData 값은 기본적으로 숨깁니다. Pod와 워크로드의 리터럴 환경 변수 값은 이름에 pass, secret, token, key, credential, auth, dsn, private, cert, database_url이 포함되면 마스킹합니다. 대소문자는 구분하지 않습니다. 다른 값은 그대로 보일 수 있습니다. `valueFrom` 참조는 보이며 값을 조회하지 않습니다.

마스킹은 최선의 노력에 따른 처리이며 시크릿의 유출 방지를 보장하지 않습니다. 로그, 메타데이터, 프로세스 정보에 예상하지 못한 형식의 자격 증명이 포함될 수 있습니다. 애초에 시크릿을 수집하지 않습니다. 감사 로그도 보호합니다. 인자와 오류에 민감한 정보가 남을 수 있습니다. 감사 기록은 변조 방지 원장이 아니며 쓰기가 실패할 때 내구성 있는 전달을 보장하지 않습니다. 컨텍스트 기한은 핸들러와 의존 구성 요소의 협력이 필요합니다. 출력 제한이 모든 리소스 고갈 위험을 없애지는 않습니다.

opsgate는 침해된 호스트, 커널, 서버 바이너리, 의존성, 관리자, 자격 증명 저장소를 방어하지 않습니다. 클라이언트를 샌드박스에 넣거나 실행한 사용자의 권한을 회수하지 않습니다. 유효 기간 내 도난당한 Bearer 토큰의 사용, 네트워크 경계의 서비스 거부, 인가된 클라이언트에 의한 정보 노출도 막지 않습니다.

## 원격 노출과 인가

HTTP는 Protected Resource Metadata와 함께 `/mcp`를 노출합니다. 인증은 필수입니다. 루프백 개발 환경을 제외하면 공개 origin에 HTTPS가 필요합니다. 신뢰할 수 있는 프록시에서 TLS를 종료하고 백엔드는 비공개로 유지합니다. [배포](deploy.md)에 설명된 검색, OAuth, 승인 경로를 전달합니다. Bearer 토큰, 쿠키, 인가 코드, 클라이언트 시크릿, 승인 URL을 로그에 남기지 않습니다.

Host 검사는 SDK의 localhost 검사를 대체합니다. 공개 요청은 명시적 포트를 포함한 `public_url`의 호스트와 일치해야 하며, 아니면 421 응답을 받습니다. 루프백 리스너는 상태 확인을 위해 루프백 Host 값도 허용합니다. Host를 보존하는 역방향 프록시는 루프백 백엔드와 함께 동작합니다. 와일드카드 리스너에는 로컬 예외가 없습니다. CORS와 MCP 애너테이션은 인가 경계가 아닙니다.

내장 OAuth는 다음 위협에 대응합니다.

- 인가 코드 가로채기: PKCE S256이 필수입니다. implicit 및 password grant는 없습니다.
- 리다이렉트 탈취: 인가와 코드 교환 시 등록된 리다이렉트 URI가 정확히 일치해야 합니다.
- 클라이언트 등록(DCR) 악용: 본문, 메타데이터, 클라이언트 수를 제한합니다. 등록 요청 빈도를 제한하며 grant와 인증 방식도 제한합니다. HTTPS 리다이렉트, 루프백 HTTP, 지원하는 네이티브 URI 스킴을 허용합니다. 용량이 가득 차면 생성 후 10분이 지난 미사용 등록을 오래된 순서로 제거합니다. 토큰이나 미완료 인가가 있는 클라이언트는 제외합니다. 등록은 도구 접근 권한을 부여하지 않습니다.
- 등록 정책: `allowed_redirect_hosts`는 리다이렉트 목적지를 제한합니다. 목록이 비어 있지 않으면 `unknown_redirect_hosts: deny`는 알 수 없는 호스트를 거부합니다. `approve`는 설정된 관리자가 `/admin/clients`에서 검토할 때까지 클라이언트를 대기 상태로 둡니다. 관리자도 허용된 사용자여야 합니다. 선택적 `notify_url`은 대기 중인 등록에 대한 JSON 알림을 최선의 노력 방식으로 받습니다. 호스트 목록이 비어 있으면 다른 유효성 조건을 만족하는 모든 리다이렉트 호스트를 허용하고 알 수 없는 호스트 정책은 무시합니다. 등록 승인은 사용자 접근 권한을 부여하거나 동의를 생략하지 않습니다.
- DCR을 통한 피싱: 동의 화면은 요청한 클라이언트, 리다이렉트 목적지, 스코프를 표시합니다. 클라이언트 이름은 신뢰할 수 없습니다. 동의가 클라이언트 소유권의 증거는 아닙니다. 사람이 목적지와 요청 권한을 확인해야 합니다. 동의 전의 인가 오류는 로컬에 표시합니다. 동의 화면 이후의 Deny는 리다이렉트할 수 있습니다.
- 코드 및 리프레시 토큰 재사용: 일회용 코드, 리프레시 토큰 교체, 재사용 탐지, 후손 토큰 계열 폐기를 적용합니다.
- 로그인 CSRF: upstream 로그인 상태를 브라우저에 바인딩합니다. 동의와 웹 승인에는 CSRF 보호를 적용합니다. OIDC는 ID 토큰도 검증합니다.
- 상태 저장소의 자격 증명 노출: 불투명 액세스 토큰/리프레시 토큰과 클라이언트 시크릿은 원본이 아닌 해시로 저장합니다. 시크릿 비교에는 상수 시간 검사를 사용합니다. 그래도 상태 파일과 백업을 보호합니다. 상태 저장 오류가 발생하면 처리를 거부합니다.

OAuth 응답은 공유 상태 잠금을 해제한 뒤 보냅니다. OAuth GET 경로는 본문을 거부하며 POST 본문 읽기의 기한은 10초입니다. 대기 중인 인가는 클라이언트당 20개 또는 전체 1000개에 도달하면 가장 오래된 항목을 제거합니다. 웹 승인 로그인은 별도의 100개 풀을 사용합니다. HTTP 접근 로그는 `/approve/<id>`를 `/approve/*`로 마스킹하고 쿼리 문자열을 생략합니다.

패스키 로그인(upstream `passkey`)에는 외부 identity provider가 필요하지 않습니다. 등록에는 일회용 초대가 필요합니다. 초대는 무작위 256비트 토큰입니다. SHA-256을 상태 파일 옆의 `0600` 파일에 저장합니다. TTL 동안 유효하며 기본값은 24h, 최대 7일입니다. 설정된 subject 하나에 바인딩되며 사용하면 삭제합니다. 첫 시작 시 opsgate는 패스키가 없는 사용자의 초대를 로그에 기록합니다. 따라서 서비스 로그를 읽을 수 있는 사람은 해당 사용자가 등록하기 전까지 그 사용자로 등록할 수 있습니다. 로그 접근을 제한하거나 대신 `opsgate passkey invite`로 초대를 발급합니다.

자격 증명에는 사용자 검증과 resident key가 필요합니다. relying party ID는 `public_url` 호스트이며, 허용하는 origin은 `public_url` 하나입니다. 각 로그인 challenge는 일회용이며 브라우저의 대기 중인 인가 쿠키에 바인딩됩니다. 서명 카운터가 증가하지 않으면 복제된 인증 장치로 간주해 거부합니다. 패스키를 잃어버리면 새 초대를 발급해야 합니다. `users`에서 사용자를 제거하면 즉시 로그인이 차단됩니다. 패스키 페이지만 스크립트를 실행합니다. `script-src 'self'` 아래의 같은 origin `/passkey.js`를 사용하며 인라인 스크립트는 없습니다.

builtin 로그인은 설정된 패스키 사용자(`passkey:<name>`), GitHub 로그인, 검증된 OIDC 이메일 ID, 또는 설정된 issuer의 정확하고 대소문자를 구분하는 `oidc:<sub>` ID만 허용합니다. Google 이메일 ID에는 Gmail/Googlemail 도메인이나 이메일 도메인과 일치하는 `hd` claim도 필요합니다. 다른 Google 주소는 변경 불가능한 subject를 사용해야 합니다. GitHub 로그인 이름이 바뀌면 로그인 허용 목록과 일치하는 사람이 달라질 수 있습니다. OIDC의 검증된 이메일을 우선 사용하거나 GitHub 허용 목록을 최신으로 유지합니다. external 모드는 검색한 JWKS로 JWT 서명을 검증하고 issuer, audience, 만료 시간, 허용된 서명 알고리즘을 검사합니다. issuer, 검색, JWKS URL에는 HTTPS가 필요하며 루프백 HTTP는 예외입니다. 선택적 외부 사용자 항목은 ID와 스코프를 제한합니다. static 모드는 SHA-256 토큰 다이제스트만 저장하며 대화형 OAuth 절차가 없습니다.

호스트/Kubernetes 쓰기에는 별도 작업 허용 목록이 필요합니다. 노트 쓰기에는 `allow_write`가 필요합니다. 이 도구에는 `ops:write`, OS/RBAC 권한, 사람의 승인이 필요합니다. dev 도구는 `dev:run`을 사용합니다. 작업 시작에는 사람의 승인이 필요하지만 취소는 위험이 낮은 명시적 예외로, 새 승인이 필요하지 않습니다. HTTP에는 `ops:read`도 필요합니다.

계획 단계는 실행 전에 대상을 검증하고 요약을 생성합니다. 클라이언트 내 확인(elicitation)은 MCP 입력 요청으로 클라이언트 내부의 결정을 받습니다. builtin 인증과 `approval.web: true`를 사용하면 클라이언트 내 확인이 없는 클라이언트는 웹 승인 링크를 받습니다. 승인자는 같은 사용자로 upstream에 로그인합니다. 승인은 만료되며 일회용입니다. 정규화한 마스킹 전 인자(`approval_id` 제외)의 SHA-256과 정확한 계획에 바인딩됩니다. 마스킹으로 요약이 바뀌면 대상을 명확히 표시할 수 없으므로 거부합니다. Kubernetes 요약에는 UID를 포함하며 Apply는 같은 호출에서 만든 계획을 받습니다. rollout은 JSON patch UID 검사를 사용하고, scale은 resourceVersion을 유지하며, Pod 삭제는 UID 사전 조건을 유지합니다. 인자가 바뀐 재시도는 승인을 재사용할 수 없습니다. 확인 없이는 쓰기를 거부합니다.

승인 시간 창은 기본적으로 꺼져 있습니다. 활성화하려면 `approval.window`를 1m–12h로 설정하고 `approval.window_tools`에 명시적 도구 이름 `path.Match` glob을 넣어야 합니다. 허용 목록이 비어 있으면 아무것도 허용하지 않습니다. 사람은 웹 승인이나 클라이언트 내 확인으로 해당하는 호출을 승인할 때 시간 창 사용을 선택할 수 있습니다. 승인 권한은 클라이언트나 대상이 아닌 정확한 사용자/도구 쌍 하나에 적용됩니다. 만료 전까지는 다른 클라이언트가 다른 인자와 대상으로 보내는 유효한 후속 호출도 의도적으로 허용합니다. `dev_task_start`에는 승인 시간 창을 활성화하지 않습니다. 모든 작업을 개별 검토합니다. 좁은 도구 허용 목록과 짧은 시간 창을 사용합니다.

승인 권한은 스코프 검사, provider 정책, 계획, 인자 제한, 요약 마스킹 검사를 우회하지 않습니다. 메모리에만 보관하며 활성 승인 권한은 최대 100개입니다. 사용해도 연장되지 않으며 재시작 시 지웁니다. 생성 시 출처 방식, 기간, 만료 시간이 담긴 별도 `window_granted` 감사 이벤트를 기록합니다. 모든 사용은 쓰기 래퍼가 `approval: window`로 감사 로그에 남깁니다. `require_web`은 여전히 브라우저에서 승인 권한을 얻도록 요구하며 stdio 쓰기를 거부합니다. 침해된 클라이언트는 개별 클라이언트 내 확인을 수락할 수 있는 것처럼 클라이언트 내 확인의 시간 창도 선택할 수 있습니다.

원시 쓰기 JSON의 기본 상한은 16 KiB입니다. 노트 create/append/replace는 528 KiB(내용/치환 입력당 256 KiB)를 허용합니다. `dev_task_start`는 48 KiB를 허용하며 프롬프트에는 별도 32 KiB 제한이 있습니다. JSON 이스케이프도 전송 제한에 포함됩니다. 승인 요약은 `max(64 KiB, argument limit + 16 KiB)`까지 허용합니다. 마스킹한 표시용 인자는 도구의 인자 제한 안에 들어야 합니다. 4 MiB를 초과하는 provider 출력은 통째로 생략합니다. 그 밖의 출력은 마스킹한 뒤 설정된 응답 상한(기본값 64 KiB)에 맞춰 자릅니다. 승인 및 동의 페이지는 이스케이프 처리하는 HTML 템플릿과 인라인 CSS를 공유합니다. 스크립트나 외부 자산은 없으며 CSRF, 교차 origin, CSP, 캐시 보호를 유지합니다. 승인 링크와 CSRF 토큰은 승인 권한 감사 이벤트에 포함하지 않습니다.

`approval.web: true`와 함께 `approval.require_web: true`를 설정하면 웹 승인을 필수로 하고 stdio 쓰기를 거부합니다. 침해된 클라이언트 UI는 클라이언트 내 확인을 자동 승인할 수 있습니다. 서버는 클라이언트가 제어하는 프롬프트를 실제 사람이 클릭했는지 확인할 수 없습니다. 프롬프트 인젝션은 여전히 모델이 쓰기를 *요청*하게 할 수 있습니다. 사람은 승인 전에 요약과 대상을 읽어야 합니다. 승인은 작업을 안전하게 만들거나 대상 상태가 그대로임을 보장하지 않습니다. OS 권한, RBAC, 좁은 허용 목록은 여전히 필수입니다. 감사 기록에는 계획, 승인 방식, 대기 결과, 웹 결정(승인 ID 접두사만 포함), 거부된 여러 왕복 검증이 포함됩니다. 다만 감사 기록의 전달은 실행의 선행 조건이 아닙니다.

## 볼트 provider

볼트 접근은 `os.Root`로 제한하고 점으로 시작하는 경로와 동기화 충돌 복사본을 제외합니다. 설정된 제외 규칙도 적용합니다. 볼트 내부의 안전한 심볼릭 링크를 지원합니다. 노트 텍스트와 파일명은 신뢰할 수 없습니다. 쓰기 계획은 대상/현재/결과 해시와 내용 미리보기 또는 diff를 표시합니다. 미리보기는 약 8 KiB로 제한합니다. 큰 생성도 잘라서 표시하며 생략한 줄 수를 명시합니다. 잘린 미리보기를 승인했다고 해서 사람이 모든 바이트를 본 것은 아닙니다.

적용 시 승인된 파일의 정체성, 해시, 크기, 수정 시간을 다시 검사합니다. 갱신은 동기화한 임시 파일을 rename으로 공개합니다. 이는 외부 편집기와의 트랜잭션이 아닌 낙관적 검사입니다. 검사와 rename 사이의 동시 외부 편집을 덮어쓸 수 있습니다. 동기화 도구의 버전 이력과 백업을 사용합니다. 생성은 동시에 생성하는 다른 작업을 덮어쓰지 않고 공개합니다. 휴지통 이동은 노트를 영구 삭제하는 대신 로컬에 복사본을 보관합니다. 볼트와 백업을 파일시스템 권한으로 보호합니다.

## dev provider

dev provider는 모든 도구에 `dev:run`을 사용하며 작업 시작에는 사람의 승인이 필요합니다. `opsdev` 같은 일반 계정으로 실행하는 별도 `opsgate dev-runner` 프로세스에 연결합니다. 이 계정에는 sudo나 클러스터 자격 증명을 주지 않습니다. 프로젝트 경로, 기준 ref, 실행 파일 경로, argv, 환경은 runner의 별도 신뢰할 수 있는 설정만이 결정합니다. 클라이언트는 설정된 이름과 크기가 제한된 프롬프트만 제출하며, 프롬프트는 stdin으로 전달합니다. Unix 소켓의 모드는 0660이며 설정된 그룹을 사용합니다. 각 연결에서 SO_PEERCRED와 계정의 그룹 소속을 검사합니다.

작업은 요청자 소유입니다. 일반 사용자는 자신의 작업만 나열하고 조회하며 로그/diff를 읽고 취소할 수 있습니다. runner `admins`에 정확히 일치하는 subject는 모든 작업에 접근하고 취소할 수 있습니다. 소켓 peer는 `X-Opsgate-User`로 사용자를 전달하는 신뢰 대상입니다. SO_PEERCRED는 최종 사용자가 아닌 peer 계정을 인증합니다. 허용된 소켓 peer는 다른 사용자나 runner 관리자를 사칭할 수 있습니다. HTTP 계정에는 소켓 디렉터리 탐색 권한을 주되 runner 설정, 상태, 자격 증명 접근이나 저장소 쓰기 권한은 주지 않습니다.

침해된 HTTP 프로세스는 작업을 직접 제출하고 서버의 사람의 승인을 우회할 수 있습니다. 다만 임의의 runner 명령이나 프로젝트 경로를 제공할 수는 없습니다. 선택된 코딩 에이전트는 여전히 임의의 악의적인 프롬프트에 따라 행동할 수 있습니다. 검증된 에이전트 샌드박스와 좁은 OS 권한을 사용합니다. Git worktree와 프로세스 그룹은 샌드박스가 아닙니다. 작업은 runner UID와 저장소 메타데이터를 공유합니다. 에이전트가 접근할 수 있는 파일, 자격 증명, 네트워크 엔드포인트는 여전히 위험에 노출됩니다. push, merge, deploy 작업은 구현되어 있지 않습니다. runner의 Git 명령은 hooks, fsmonitor, 전역/시스템 설정, 서명을 비활성화합니다. diff는 외부 diff/텍스트 변환도 비활성화합니다. 저장소 로컬 Git 설정을 신뢰할 수 있게 유지합니다.

작업 로그와 최종 메시지, diff는 신뢰할 수 없는 데이터입니다. API 출력에는 제한과 최선의 노력에 따른 마스킹을 적용합니다. 하지만 원본 프롬프트/로그/출력과 커밋 메시지는 디스크에 민감한 정보를 남길 수 있습니다. 저장소, 상태, 백업을 보호합니다. 상태 저장에 실패하면 작업 전달을 중단합니다. 보존 관리는 완료된 worktree와 기록을 삭제하지만 브랜치는 유지합니다. 작업 수/출력 상한은 저장소 크기나 모든 리소스 소비를 제한하지 않습니다. 서비스 제한과 정리 정책을 설정합니다. [설정, 작업 흐름, 위험](dev.md)을 참고합니다.

## 지원 버전

프로젝트가 0.x인 동안 보안 수정과 지원은 최신 개발 버전에 집중하며 최선의 노력 방식으로 제공합니다. 이전 0.x 릴리스의 유지보수 기간은 보장하지 않습니다.

## 취약점 신고

[GitHub Security Advisories](https://github.com/gkdis6/opsgate/security/advisories/new)로 비공개 신고합니다. 저장소의 Security 페이지에서 **Report a vulnerability**를 선택합니다. 영향을 받는 리비전, 시크릿을 제거한 설정, 영향, 재현 단계를 포함합니다. 취약점에 대해 공개 이슈를 열거나 자격 증명을 공개하지 않습니다. 유지보수자는 조사와 공개 절차를 비공개로 조율합니다. 응답은 최선의 노력 방식으로 제공합니다.
