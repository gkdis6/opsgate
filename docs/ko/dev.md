# dev provider를 통한 코딩 작업

[English](../dev.md)

이 provider는 선택 사항이며, 구현은 마쳤지만 아직 실험 단계입니다.

`opsgate dev-runner`는 설정된 코딩 에이전트를 별도 Linux 계정으로 실행합니다. 외부에 공개하는 MCP 서버는 Unix 소켓으로 runner에 연결하며, runner에 설정된 프로젝트와 에이전트 이름만 선택할 수 있습니다. 작업마다 `opsgate/<id>` 브랜치와 새 Git worktree를 만들며, 자동으로 푸시하거나 병합, 배포하지는 않습니다.

## 계정과 저장소 설정

sudo 권한, 클러스터 자격 증명, 프로덕션 비밀값, 배포 키가 없는 전용 `opsdev` 계정을 만들고, HTTP 서버의 `opsgate` 계정과 분리하세요. 신뢰할 수 있는 에이전트 바이너리는 절대 경로에, Git은 `/usr/bin/git`에 설치하세요. 필요하면 `opsgate` 그룹을 만들고, 소켓의 그룹을 설정할 수 있도록 `opsdev`를 이 그룹에 추가하세요. 그룹 구성원을 변경한 뒤에는 서비스를 재시작하세요.

서비스를 시작하기 전에 `HOME=/var/lib/opsgate-dev`로 설정한 `opsdev` 계정의 대화형 세션에서 Codex와 Claude 중 사용할 에이전트의 로그인 명령을 실행하세요. 자격 증명은 이 홈 디렉터리에 비공개로 보관하고, YAML, 에이전트 argv, 프롬프트, MCP 서버 환경에는 토큰을 넣지 마세요. 함께 제공하는 서비스는 이 HOME을 설정하고 다른 사용자의 홈 디렉터리를 숨깁니다.

허용 목록에 있는 각 저장소와 그 `.git` 디렉터리를 `opsdev`가 탐색하고 읽고 쓸 수 있도록 권한을 주세요. 예를 들어 관리자는 `/srv/projects/example`에 특정 사용자를 지정한 ACL을, 새 파일에 적용할 기본 ACL을, 상위 디렉터리에 탐색 ACL을 설정할 수 있습니다. 먼저 기존 그룹과 ACL 권한을 검토하세요. Git worktree는 원본 저장소의 객체와 ref를 공유하므로 worktree에만 쓰기 권한을 주어서는 충분하지 않습니다. HTTP 계정에는 저장소, runner 상태, 에이전트 자격 증명, runner 설정을 수정할 권한을 주지 마세요.

[dev-runner.example.yaml](../../deploy/dev-runner.example.yaml)을 `/etc/opsgate/dev-runner.yaml`로 복사하세요. 파일은 root 소유로 설정하고 `opsdev`가 읽을 수 있게 하되, 서버 계정과 runner 계정 모두 쓸 수 없게 하세요. 상위 디렉터리의 접근 권한도 제한하세요. 프로젝트 이름, 절대 경로, base ref, 고정된 에이전트 argv를 정확히 지정하세요. argv에서는 `{workdir}`와 `{output}`만 치환하며, 프롬프트는 `prompt.txt`에 비공개로 저장한 뒤 stdin으로 전달합니다.

에이전트 환경에는 HOME, 고정된 PATH, LANG, TERM, 운영자가 설정한 `env` 항목만 들어갑니다. 이 항목은 신뢰할 수 있는 설정으로 취급하며 기본값을 덮어쓸 수 있으므로, 에이전트에 필요한 항목만 설정하세요.

## 서비스 설치와 provider 활성화

[opsgate-dev-runner.service](../../deploy/systemd/opsgate-dev-runner.service)를 설치하고, 주석 처리된 `ReadWritePaths=`에 설정한 저장소를 모두 추가하세요. 이 설정이 없으면 `ProtectSystem=strict` 때문에 Git이 그 위치에 ref와 worktree 메타데이터를 쓸 수 없습니다. 서비스는 `/var/lib/opsgate-dev`를 비공개로 관리하고, `/run/opsgate-dev`를 `opsdev:opsdev` 소유, 권한 0750으로 생성합니다.

런타임 디렉터리의 탐색 권한은 서버 그룹에만 주세요. systemd 드롭인을 사용하면 RuntimeDirectory를 생성한 뒤 다음 명령을 실행할 수 있습니다. setfacl 경로는 환경에 맞게 조정하세요.

```ini
[Service]
RuntimeDirectoryPreserve=yes
ExecStartPre=/usr/bin/setfacl -m g:opsgate:--x /run/opsgate-dev
```

디렉터리 소유자인 `opsdev`는 root 권한 없이 이 ACL을 적용할 수 있습니다. 소켓 자체는 `opsdev:opsgate` 소유이며 권한은 0660입니다. 연결을 수락할 때마다 Linux `SO_PEERCRED`도 확인하므로, runner와 UID가 같거나 `socket_group`이 기본 그룹 또는 보조 그룹인 UID만 연결할 수 있습니다. 소켓 그룹 권한만으로는 상위 디렉터리를 탐색할 수 없어 런타임 디렉터리 ACL이 필요합니다. HTTP 계정을 `opsdev`에 추가하거나 상태 디렉터리 권한을 완화하지 마세요.

서버는 파드에서 실행하므로, runner가 실행되는 노드에 파드를 배치하고 `/run/opsgate-dev`를 `hostPath`로 마운트해 소켓에 접근해야 합니다. 파드의 `runAsGroup`을 호스트의 `socket_group` GID로 설정하세요. `internal/devrunner/peer_linux.go`의 피어 검사는 일치하는 기본 그룹을 허용하고, 위 런타임 디렉터리 ACL은 그 그룹에 탐색 권한을 줍니다. 같은 드롭인에 `RuntimeDirectoryPreserve=yes`도 설정하세요. 그렇지 않으면 runner가 중지될 때 systemd가 디렉터리를 삭제하며, 파드의 마운트는 이전 디렉터리를 계속 가리킵니다. 이 파드와 runner 간 연결 구성은 실험적이며 아직 실행해 확인하지 않았습니다.

systemd로 runner를 활성화하고 시작한 뒤 MCP 서버를 설정하세요.

```yaml
providers:
  dev:
    enabled: true
    runner_socket: /run/opsgate-dev/runner.sock
```

도구를 사용할 사용자에게 `dev:run`을 주세요. 현재 HTTP 접근에는 `ops:read`도 필요합니다. 작업을 시작하려면 기존 클라이언트 내 확인(elicitation)/웹 승인 절차로 사람의 승인을 받아야 합니다. 읽기와 취소 도구에도 `dev:run`이 필요하지만, 별도로 승인을 받을 필요는 없습니다.

작업 소유자는 요청자이며, 일반 사용자는 자신의 작업만 보고 취소할 수 있습니다. runner의 `admins` 목록에 subject가 정확히 일치하는 사용자는 모든 작업을 보고 취소할 수 있습니다. 이 목록에는 builtin subject, `static:<token-name>`, 외부 사용자 클레임 값, stdio 사용자 레이블 중 실제 호출자와 정확히 일치하는 식별자를 사용하세요. 이 목록은 내장 OAuth의 클라이언트 등록 관리자 목록과 별개입니다.

접근이 허용된 소켓 연결 상대는 `X-Opsgate-User`로 사용자 식별자를 전달하며, runner는 이 값을 신뢰하고 최종 사용자의 토큰을 인증하지 않습니다. 접근이 허용된 연결 상대는 누구나 작업 소유자나 관리자를 사칭할 수 있으므로, 이를 고려해 소켓 접근 그룹의 구성원을 관리하세요.

`dev_task_start`에는 승인 시간 창을 활성화하지 말고, 작업마다 따로 검토하세요. runner가 중단되면 dev 도구 호출에서 오류를 보고하지만, MCP 서버의 시작 자체를 막지는 않습니다. 포그라운드에서 문제를 진단하려면 다음 명령을 실행하세요.

```sh
opsgate dev-runner -config /etc/opsgate/dev-runner.yaml
```

Codex와 Claude의 샌드박스 설정은 설치된 에이전트에 따라 다르므로, 실제로 서비스를 실행할 계정과 보안 강화 설정에서 확인하세요. Bubblewrap 기반 샌드박스에는 일반 사용자 권한으로 생성할 수 있는 사용자 네임스페이스가 필요하므로, 이 유닛에 `RestrictNamespaces`나 `PrivateUsers`를 추가하지 마세요. runner는 worktree와 프로세스 그룹을 만들지만, OS 샌드박스를 직접 구현하지는 않습니다.

## 작업 흐름과 제한

1. `dev_projects`를 호출해 프로젝트, base ref, 에이전트, 제한을 확인하세요.
2. 프로젝트, 에이전트, 전체 요구 사항을 지정해 `dev_task_start`를 호출하고, 승인하기 전에 요약과 요구 사항을 정확히 검토하세요. 승인은 샌드박스와 로컬 정책이 허용하는 명령을 포함해 에이전트의 작업 전체에 적용됩니다.
3. `dev_task_status`, `dev_task_log`, `dev_task_diff`로 진행 상황을 확인하고, 출력과 diff는 신뢰할 수 없는 데이터로 취급하세요. 로그는 원시 바이트 기준의 `next_offset`을 반환합니다. MCP 출력 상한 때문에 JSON이 잘리지 않도록 페이지 크기를 작게 요청하세요. 실행 중인 작업의 diff에는 Git이 추적하는 파일의 변경 사항이 표시되며, 새 파일은 작업 완료 시 스테이징한 뒤에 나타납니다.
4. 필요하면 `dev_task_cancel`로 취소하세요. 통합 여부를 결정하기 전에 브랜치를 직접 검토하고 자체 검사를 실행하세요.

작업 상태는 queued에서 running으로 바뀐 뒤 succeeded, failed, canceled, timed_out 중 하나로 끝납니다. runner를 재시작하면 미완료 기록은 interrupted로 바뀌며, 작업을 다시 실행하지 않습니다. 종료할 때는 실행 중이거나 대기 중인 작업을 취소하고 프로세스 그룹이 종료될 때까지 기다립니다. 취소하거나 제한 시간을 넘기면 SIGTERM을 보내고 최대 10초를 기다린 뒤 SIGKILL을 보냅니다. systemd도 유닛을 중지할 때 남은 서비스 프로세스를 종료합니다.

runner는 기준 커밋을 고정하고 새 브랜치와 worktree를 만든 뒤 설정된 실행 파일/argv만 실행합니다. 일반적인 종료 절차에서는 에이전트의 종료 코드가 0이 아닌 경우에도 `git add -A`로 변경 사항을 스테이징하고 `opsgate dev-runner <dev-runner@localhost>` 이름으로 커밋합니다. 커밋 메시지에는 작업 ID와 요구 사항의 첫 줄을 넣으며, 첫 줄은 최대 72자로 제한합니다.

작업을 취소하거나 제한 시간을 넘긴 경우에도 에이전트 그룹이 멈춘 뒤에는 그때까지 수정한 내용을 커밋하려고 시도하며, 이 마무리 작업에는 별도로 30초 제한을 둡니다. Git 명령이 실패하거나 runner가 중단되면 보관된 worktree에 커밋하지 않은 변경 사항이 남을 수 있습니다. runner의 Git 명령에서는 Git hook, fsmonitor, 전역/시스템 Git 설정, 커밋 서명을 끄고, diff에서는 외부 명령과 텍스트 변환도 끕니다. 설정된 필터를 포함해 저장소의 로컬 Git 설정은 신뢰할 수 있는 상태로 유지해야 합니다.

프롬프트 크기는 1바이트에서 32 KiB이며, 요청자 식별자는 최대 256바이트입니다. dev_task_start는 MCP 인자를 최대 48 KiB, 승인 요약을 최대 64 KiB까지 허용합니다. JSON 이스케이프도 전송 크기 제한에 포함되므로, 이스케이프가 많으면 실제로 전달할 수 있는 프롬프트는 더 짧아질 수 있습니다.

로그는 작업당 20 MiB로 제한하며, 이를 넘는 출력은 계속 읽되 버립니다. 로그 페이지와 diff는 전체 원본에서 비밀 범위를 탐지한 뒤 원본 텍스트를 최대 256 KiB까지 선택해 마스킹하며, 마스킹한 응답도 JSON 인코딩 전에 256 KiB로 제한합니다. 원본이 20 MiB를 넘으면 일부만 검사하지 않고 조회를 거부합니다. 이후 MCP가 자체 출력 상한을 적용합니다. 최종 메시지는 읽을 수 있는 일반 출력 파일의 첫 256 KiB 또는 로그의 마지막 8 KiB를 사용하되 전체 원본에서 비밀 범위를 탐지한 뒤 해당 부분을 마스킹하며, 원본이 20 MiB를 넘으면 생략 안내를 반환합니다.

기본 제한 시간은 1시간, 동시 실행 수는 1개(최대 8개), 보관 작업 수는 100개입니다. 보관 한도에 도달하면 새 작업을 받기 전에 완료된 작업 중 가장 오래된 작업의 기록, 로그, worktree를 삭제하며, Git 브랜치는 남겨 둡니다. 보관 중인 작업이 모두 대기 중이거나 실행 중이면 새 작업을 거부합니다. 이전 프로젝트 정의는 보관 정책에 따라 그 프로젝트의 작업이 모두 삭제될 때까지 유지하세요.

작업 기록은 `tasks.json`에 원자적으로 쓰고 동기화해 재시작 후에도 유지합니다. 저장에 실패하면 작업 배정을 중단하고 새 작업을 실행하지 않습니다. 배타적 잠금으로 두 runner가 같은 상태 디렉터리를 사용하지 못하게 합니다.

## 위험과 유지 관리

작업을 승인한 뒤에는 runner 계정과 에이전트 샌드박스가 보안 경계가 됩니다. 에이전트는 악성 프롬프트를 명령 실행 요청으로 해석할 수 있습니다. worktree는 수정 내용을 분리하지만, 자격 증명, 공유 Git 객체 저장소, 다른 저장소, 네트워크 접근, 같은 UID로 실행하는 다른 작업까지 격리하지는 않습니다.

공격자가 HTTP 프로세스를 장악하면 자체 승인 로직을 우회해 소켓으로 허용 목록에 있는 작업을 제출할 수 있습니다. runner 계정의 권한을 최소한으로 유지하고 에이전트 샌드박스를 검증하세요. 신뢰 수준이 다르면 runner와 계정도 분리하세요. 이 계정에 높은 권한의 자격 증명이나 신뢰할 수 있는 배포 hook을 주지 마세요. 샌드박스가 허용하면 에이전트는 OS 기능을 사용해 의도적으로 프로세스 그룹을 벗어날 수 있습니다. 프로세스 그룹은 수명 주기를 제어하는 수단이며, 실행을 격리하지는 않습니다.

프롬프트, 원시 로그, 출력 파일, 커밋에는 민감한 정보가 들어갈 수 있습니다. API 마스킹이 모든 비밀값을 가린다고 보장하지 않으므로 상태, 저장소, 백업을 보호하세요. 보관 정책에 따라 정리한 뒤에도 브랜치는 남으므로 운영자가 별도의 정리 정책을 마련해야 합니다. 파일/로그 크기와 작업 수 제한만으로는 전체 저장소 증가량, 디스크 공간, 모든 CPU/메모리 사용량을 제한할 수 없습니다. 계정/서비스에 리소스 제한을 적용하고 저장 공간을 모니터링하세요. 아직 정식 출시 전인 기능이므로 배포하기 전에 코드와 의존성을 검토하세요.
